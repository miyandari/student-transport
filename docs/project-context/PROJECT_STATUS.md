## وضعیت منطق Boarding

منطق فعلی به این صورت طراحی شده است:

### درخواست عادی دانشجو

اگر صندلی خالی باشد:

```text
Request → تأیید خودکار → Boarding
```

اگر صندلی پر باشد ولی ظرفیت ایستاده وجود داشته باشد و ایستادن مجاز باشد:

```text
Request → تأیید خودکار → Boarding به‌صورت ایستاده
```

اگر تمام ظرفیت پر باشد:

```text
Request → Waitlist
```

در درخواست عادی، راننده نباید مجبور باشد دائماً تلفن خود را بررسی و درخواست‌ها را تأیید کند.

### درخواست QR

در QR بدون رزرو قبلی:

```text
Student Scan QR
        ↓
Boarding Request
        ↓
Driver Approval
        ↓
Approve / Reject
```

در صورت تأیید:

```text
boarding_without_reservation
```

ثبت می‌شود و این حالت نباید باعث No-Show شود.

## وضعیت Waitlist

درخواست‌های عادی که ظرفیت ندارند وارد Waitlist می‌شوند.

با آزادشدن ظرفیت، سامانه می‌تواند درخواست‌های Waitlist را بررسی و در صورت امکان به‌صورت خودکار ارتقا دهد.

پس از ارتقا:

- Boarding ثبت می‌شود.
- درخواست تأیید می‌شود.
- Notification برای دانشجو ارسال می‌شود.

Waitlist به‌خودی‌خود No-Show محسوب نمی‌شود.

---

## وضعیت No-Show

No-Show هنگام تکمیل Trip بررسی می‌شود.

اگر:

- Reservation فعال وجود داشته باشد،
- دانشجو سوار نشده باشد،
- TripPassenger برای آن Reservation وجود نداشته باشد،

No-Show ثبت می‌شود.

هر No-Show:

```text
no_show_count += 1
negative_score += 1
```

مسدودی:

| تعداد No-Show | مسدودی |
|---|---:|
| اول | بدون مسدودی |
| دوم | ۱ روز |
| سوم | ۳ روز |
| چهارم | ۵ روز |
| پنجم | ۷ روز |
| ششم و بیشتر | ۱۴ روز |

برای جلوگیری از ثبت جریمه تکراری، AuditLog بررسی می‌شود.

لغو Reservation و Waitlist نباید No-Show محسوب شوند.

## وضعیت Incident

## اقدام فوری

قبل از ادامه توسعه، تغییرات فعلی Local باید در یک Commit محلی تثبیت شوند.

دستورها:

```powershell
cd F:\project\student-transport
git status
git add .
git commit -m "Complete backend boarding, notification and trip lifecycle updates"
git status
git log -1 --oneline
```

فعلاً Push به GitHub انجام نشود، مگر اینکه کاربر صراحتاً درخواست کند.

## مرحله فعلی پروژه

پروژه در این نقطه قرار دارد:

```text
Backend
  ↓
پیاده‌سازی قابلیت‌های اصلی
  ↓
تثبیت منطق کسب‌وکار
  ↓
بازبینی API و Service
  ↓
تست سناریوهای اصلی
  ↓
تکمیل Backend
  ↓
Frontend / اپ دانشجو / اپ راننده
```

در حال حاضر تمرکز اصلی باید روی **تثبیت Backend و تست سناریوهای واقعی** باشد، نه طراحی مجدد قابلیت‌هایی که قبلاً پیاده‌سازی شده‌اند.

## قانون مهم برای ادامه پروژه

در ادامه توسعه:

1. ابتدا وضعیت فایل فعلی بررسی شود.
2. اگر فایل تغییری لازم ندارد، دوباره برای کاربر ارسال نشود.
3. اگر فایلی تغییر می‌کند، کل فایل در یک Code Block ارائه شود.
4. کد به چند تکه تقسیم نشود مگر واقعاً ضروری باشد.
5. تغییرات Migration فقط در صورت نیاز واقعی انجام شود.
6. نسخه Local نسبت به GitHub اولویت دارد.
7. بدون درخواست صریح کاربر Commit یا Push انجام نشود.
8. توضیحات طولانی داده نشود و تمرکز روی اجرای مرحله بعد باشد.
